- **Command hooks using POSIX syntax need `"shell": "bash"` explicitly**, even on Windows with Git Bash installed — hooks have their own shell detection and silently fall back to `cmd.exe` (symptom: `'x' is not recognized as an internal or external command`, where `x` is the first token of the POSIX script).
- **`"shell": "bash"` only names the shell; Windows still has to locate Git Bash, and on this machine it cannot.** Claude Desktop launches from Explorer with the plain Windows `PATH`, which carries `C:\Program Files\Git\cmd` (holds `git.exe` only) but neither `Git\bin` nor `Git\usr\bin`, where `bash.exe` actually lives — so a hook that runs under the terminal-launched CLI can still hit the `cmd.exe` fallback under Desktop. Pin it in the **user-level** `~/.claude/settings.json` `env` block (machine property, not repo property — a Windows absolute path in the checked-in project settings is wrong for every macOS/Linux contributor): `"CLAUDE_CODE_GIT_BASH_PATH": "C:\\Program Files\\Git\\bin\\bash.exe"`. Two traps: the variable is silently ignored unless the filename is exactly `bash.exe`, `sh.exe`, `bash`, or `sh` (Git's `git-bash.exe` launcher is rejected and auto-detection resumes as if unset), and the only `bash` on the Windows `PATH` here is `C:\WINDOWS\system32\bash.exe` — the WSL launcher, which resolves the project as `/mnt/e/...` and would break `$CLAUDE_PROJECT_DIR` even if it were selected. Env changes are read at launch, so Desktop needs a full restart.
- **Exec form (`"args": []`) does not make a `.sh` hook portable to Windows.** It bypasses the shell, and Windows cannot execute a `.sh` without an interpreter — a shell-file hook needs Git Bash resolvable either way.
- **Don't simplify `WorktreeCreate` back to a bare `bun install`** — the stale-dir `rm -rf`, the `git worktree prune`, the `tr -d '\r'` on `name`, and warn-don't-exit on `bun install` failure each fixed a real breakage (#441, #442).
- **Claude Code cloud environments (claude.ai/code) can't install deps via the environment's own setup script** — the cloud image ships Bun preinstalled, so `curl -fsSL https://bun.sh/install` 403s (bun.sh isn't on the Trusted network allowlist, which only covers package registries/GitHub) and is unnecessary anyway. Worse, `bun install` itself has documented proxy-compatibility issues when run from the setup-script phase (all cloud egress routes through a security proxy Bun doesn't handle cleanly). Anthropic's own fix is a repo-level `SessionStart` hook instead — see `scripts/install-cloud-deps.sh` (guarded on `CLAUDE_CODE_REMOTE == "true"`) wired into `.claude/settings.json`'s `hooks.SessionStart`. This is the documented workaround, not a guaranteed fix — if `bun install` still fails inside the hook, that's a known unresolved limitation per https://code.claude.com/docs/en/claude-code-on-the-web, not a misconfiguration.
