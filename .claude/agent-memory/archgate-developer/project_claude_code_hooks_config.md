- **Put no shell syntax in a hook command — `"shell": "bash"` is not honoured on every surface.** The Claude desktop app on Windows runs hook commands under `cmd.exe` even when the hook declares `"shell": "bash"` and `CLAUDE_CODE_GIT_BASH_PATH` points at a valid `Git\bin\bash.exe` in user-level settings; the terminal CLI on the same machine honours it. Symptom: `'x' is not recognized as an internal or external command`, where `x` is the first token of the POSIX script (`cmd.exe` splits on `=`, so `name=$(...)` reports as `'name'`). Keep every hook command to `bun run hook:<name>` — one token, no `$VAR`, no `;`, no `$(...)`, no quoting — with the logic in `scripts/*.ts`. That string is valid under Bash, `cmd.exe` and PowerShell alike, and `bun run` walks up to find `package.json`, so it does not depend on the hook's working directory either.
- **A shell-free hook command is also the only way to prove which shell ran it.** `~/.claude/debug` holds nothing for hooks and the desktop app writes no hook log, so the sole signal is the error text. A deliberately-named first token turns that into a readable answer — an unused `some_descriptive_name=1` assignment prefix makes `cmd.exe` print `'some_descriptive_name' is not recognized`. Useful for one diagnostic round; it has no place in a command that already avoids shell syntax.
- **Windows PATH traps behind all of this:** Git for Windows puts only `Git\cmd` (which holds `git.exe`, not `bash.exe`) on `PATH`, so `bash` there resolves to `C:\WINDOWS\system32\bash.exe` — the WSL launcher, which sees the repo as `/mnt/e/...` and would break `$CLAUDE_PROJECT_DIR` if selected. `CLAUDE_CODE_GIT_BASH_PATH` is silently ignored unless the filename is exactly `bash.exe`, `sh.exe`, `bash` or `sh` (Git's `git-bash.exe` launcher is rejected and auto-detection resumes as if unset). `bun` and `jq` do resolve from the plain Windows `PATH` here (bun via `~/.proto/shims`).
- **Exec form (`"args": []`) does not make a `.sh` hook portable to Windows.** It bypasses the shell, and Windows cannot execute a `.sh` without an interpreter — a shell-file hook needs Git Bash resolvable either way.
- **Don't simplify `WorktreeCreate` back to a bare `bun install`** — the stale-dir `rm -rf`, the `git worktree prune`, the `\r` strip on `name`, and warn-don't-exit on `bun install` failure each fixed a real breakage (#441, #442).
- **Hooks run with the working directory set to the project root**, and settings changes take effect immediately — no session restart needed to pick up an edited hook. Both confirmed by probe; a hook added to the gitignored `.claude/settings.local.json` fires without a reload, which makes it the clean place to test hook behaviour without touching the tracked file.
- **Claude Code cloud environments (claude.ai/code) can't install deps via the environment's own setup script** — the cloud image ships Bun preinstalled, so `curl -fsSL https://bun.sh/install` 403s (bun.sh isn't on the Trusted network allowlist, which only covers package registries/GitHub) and is unnecessary anyway. Worse, `bun install` itself has documented proxy-compatibility issues when run from the setup-script phase (all cloud egress routes through a security proxy Bun doesn't handle cleanly). Anthropic's own fix is a repo-level `SessionStart` hook instead — see `scripts/session-start.ts` (guarded on `CLAUDE_CODE_REMOTE == "true"`) wired into `.claude/settings.json`'s `hooks.SessionStart`. This is the documented workaround, not a guaranteed fix — if `bun install` still fails inside the hook, that's a known unresolved limitation per https://code.claude.com/docs/en/claude-code-on-the-web, not a misconfiguration.
