`archgate check`'s `[briefing]` / `briefingWarnings` output only gives an ADR ID, section name, and length vs. the `review-context` truncation cap (2000 chars) — it never shows the ADR's own prose. A flagged ADR's Exceptions section can carry a "Documented briefing-budget overflow ... MUST NOT be shortened further" clause written by a prior session. **Read that as "not yet resolved," not "permanently unresolvable."** A prior session writing that clause usually means nobody had tried relocating the content yet, not that relocation is impossible — see [[pick-the-right-enforcement-layer]] for the general principle that this repo's own governance text is itself editable when the underlying constraint (the 2000-char cap) can be satisfied without losing anything.

**Why:** asked to "fix the briefing violations" (2026-07-26), a bare read of the check JSON made all 7 warnings look identical. Four of five flagged ADRs (ARCH-005, ARCH-022 ×2, ARCH-024 ×2, GEN-004) had a "MUST NOT be shortened further" clause; the first pass wrongly treated that as final and left them alone. The user then pointed out the sections CAN shrink without losing semantics by moving detail to sections `review-context` doesn't cap — Decision and Do's/Don'ts are the only capped sections; Context, Consequences, Compliance and Enforcement, and any new section are not. Applying that closed all 7 warnings, `bun run validate` still passed, and four independent per-file agents (given the exact original text, told to diff it against the edited file) confirmed no MUST/DON'T rule, enumerated identifier, or cross-reference was actually lost — only relocated.

**The technique that works, for a Decision or Do's/Don'ts section over budget:**

1. Identify what's the bare rule (a MUST/DON'T statement, an identifier that's part of the rule itself — e.g. a guardrail step's function name) vs. what's elaboration (why, exact mechanics, enumerated lists that support but aren't themselves the rule).
2. Keep the bare rule in the capped section, as terse as possible, with a short pointer like "(Key Definitions)" or "(Consequences: ...)".
3. Move the elaboration verbatim (or near-verbatim) into a new `## Key Definitions` section — insert it between `## Decision` and `## Do's and Don'ts` if the ADR doesn't already have a natural home for the detail — or extend an existing Context/Consequences/Compliance paragraph that already discusses the same topic. Prefer extending an existing paragraph over creating a new one.
4. **This takes many iterations to land under the cap exactly** — trimming Decision's prose alone can require 10-15 successive edits, each shaving one clause's wording, re-running `bun run src/cli.ts check` (or grep the specific ADR's `briefingWarnings` entry out of its JSON) after every edit to see the new length. There is no way to predict the exact character count from reading the markdown; measure after every edit. Budget for this — a single 10,000-character Decision section (ARCH-022 in this session) took roughly 40 edit-measure cycles across both its Decision and Do's/Don'ts sections.
5. Once a section is under budget, **verify before moving on**: spawn an independent agent (haiku is sufficient) with the ORIGINAL section text pasted in and told to confirm every fact/identifier from it is still findable anywhere in the current file. Don't trust your own read of the diff — a self-check misses your own oversights.
6. Reword the ADR's own "MUST NOT be shortened further" Exceptions clause to state what actually happened (content relocated, not cut) once the section passes. Leaving the stale clause in place is itself now a factual error in the ADR.

**How to apply:** on any "fix the archgate check / briefing warnings" request, don't stop at "the ADR says don't shorten this" — that's the starting point for asking the user whether relocation is wanted, not a hard stop. If they confirm (as here), follow the five-step loop above per ADR, smallest first.
